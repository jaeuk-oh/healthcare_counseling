# 보건소 의료비 지원 상담 AI

> 도메인 규정을 LLM과 코드의 역할로 분리한 업무형 AI 시스템

하남시 보건소 의료비 지원 전화 상담을 AI가 1차 응대하는 시스템입니다.
시민이 자신의 상황을 말하면, AI 상담사가 해당 가능한 지원 정책을 분류하고
체크리스트로 자격 요건을 순차 확인한 뒤, **전화로 판정할 수 없는 항목은
판정하지 않고 내방 안내로 마무리**합니다. 정책 분류 → 조건 확인 → 전화로
확정 가능한지 판단 → 상담 또는 내방 전환으로 이어지는 이 흐름이 이 시스템의
1차 트리아지 역할입니다.

**"LLM이 상담을 잘하게 만드는 것"이 이 프로젝트의 목표가 아니었습니다.**
처음 목표는 그것이었고, 실제로 상담을 자동화하는 데는 큰 어려움이 없었습니다.
문제는 자격 판정이 자주 틀린다는 것이었고, 원인을 하나씩 따라가 보니 전부
"LLM에게 어디까지 맡기고 어디서부터 코드가 강제해야 하는가"의 경계를 정하지
않은 곳에서 나왔습니다. 그래서 이 프로젝트가 실제로 하는 일은
**업무 규정 중 무엇을 LLM에게 해석하게 하고 무엇을 시스템이 강제해야 하는지,
그 경계를 도메인 지식으로 정의하는 것**입니다.

---

## 1. 왜 이 문제인가

- **대상 사용자**: 하남시 보건소 의료비 지원 전화 상담을 받는 **상담원**입니다.
  시민이 직접 쓰는 셀프서비스가 아니라 상담원을 보조하는 내부 도구입니다.
- **업무 상황**: 상담원은 한 통화 안에서 시민의 상황(진단명, 보험 유형, 진단·검진
  시점 등)을 파악하면서 동시에 정책별 소득기준·대상질환·신청조건·예외조건을
  대조해야 합니다.
- **기존 프로세스**: 사람이 여러 정책 문서를 오가며 조건을 암산으로 대조합니다.
- **문제**: 이 상담은 다음 두 가지가 동시에 성립해야 하는데, 실제로는 반대로
  가기 쉽습니다.
  1. **틀린 안내는 시민에게 직접 피해를 줍니다.** 자격이 안 되는데 "될 것
     같다"고 안내하면 시민이 서류를 들고 헛걸음하고, 반대의 경우 받을 수 있는
     지원을 놓칩니다.
  2. **전화로는 판정할 수 없는 항목이 있습니다.** 소득·재산은 서류로만 확인
     가능한데, LLM은 대화 맥락만으로 "소득 기준을 충족하신 것 같다"고
     단정해버리기 쉽습니다.
- **근거**: 필자는 하남시 보건소 만성질환팀 상담원으로 근무한 경험이 있고,
  아래 두 실패 유형은 실제 업무에서 반복적으로 관측한 것입니다(§7 도메인
  암묵지에 구체 사례로 기록).

즉, **LLM의 유연함이 그대로 위험이 되는 영역**입니다. 그래서 이 시스템은
판단을 LLM에 맡기되, 틀리면 피해가 큰 지점만 코드로 묶었습니다.

**범위를 처음부터 이렇게 좁힌 것은 아닙니다.** 초기 아이디어는 "시민이 직접
쓰는 복지 상담 챗봇"에 가까웠습니다. 그런데 실제로 누가 이 판단을 필요로
하는지 짚어보니, 정책 조건을 대조하는 건 상담원의 업무였고 시민이 직접 그
판단을 내릴 이유가 없었습니다. 그래서 대상을 "상담원을 보조하는 내부 도구"로,
범위를 국가 전체 복지 정책에서 "보건소 의료비 지원 3종"으로 좁혔습니다.

---

## 2. Problem Discovery — 자동화가 아니라 판단 경계였다

구현을 시작할 때는 "의료비 지원 상담을 자동화한다"가 목표였습니다. 상담 흐름
자체를 만드는 건 어렵지 않았습니다. 실제로 반복해서 문제를 일으킨 지점은
**LLM이 정책을 몰라서가 아니라, 판정하면 안 되는 것을 판정해버리는 것**이었습니다.

- 건강보험 가입자를 확인하자마자 상담을 끝내버린 최초 구현 (§7-4)
- 정책 문서 안에 남아 있던 상반된 두 문장 중 더 단정적인 쪽을 그대로 따라간 것 (§7-5)
- 소득 기준을 대화 맥락만으로 충족했다고 판단할 뻔한 것 (§4-1)

이 각각은 "AI가 상담을 못해서"가 아니라 **"어디까지가 LLM의 판단이고 어디부터
시스템이 강제해야 하는지"를 정하지 않아서** 발생했습니다. 그래서 이 프로젝트의
실제 산출물은 상담 스크립트가 아니라 아래 §4의 역할 분리와 §5의 가드레일입니다.
이 발견이 이 프로젝트를 넘어 어디로 이어지는지는 §10에서 다시 다룹니다.

## 3. 핵심 설계

### 3.1 아키텍처 — RAG + 체크리스트 상태 머신

이 시스템에서 RAG의 역할은 검색 정확도를 높이는 것이 아니라 **정책 지식을
제공하는 것**입니다. 대상 정책 문서가 3개뿐이라 검색의 선별 기능은 의도적으로
쓰지 않고 매 턴 전체 문서를 컨텍스트로 전달하며(`top_k = 전체 문서 수`),
실제 상담 행동을 결정하는 것은 **function calling 기반 체크리스트 상태 머신과
코드 레벨 가드레일**입니다.

```
[첫 턴] 사용자 발화
   │
   ▼
classify()  ── GPT function calling으로 해당 가능한 정책 선별
   │            (암의료비지원 / 희귀질환의료비지원 / 국가암검진)
   ▼
선별된 정책의 체크리스트를 met:None 으로 초기화
   │
   ▼
[매 턴] 단일 LLM 호출로
   ├─ 상담사 답변 생성
   └─ 체크리스트 상태 업데이트
   │
   ▼
코드 레벨 가드레일 적용 (§4)
   │
   ▼
전화로 끝낼 수 없는 항목(소득·재산)은 내방 안내로 핸드오프
```

**API 설계: 상태는 클라이언트가 보유.** `/chat` 엔드포인트는 매 턴
`messages`(전체 대화 이력)와 `checklist`(현재 체크리스트 상태)를 클라이언트로부터
받아 처리합니다. 서버는 별도 세션 상태를 저장하지 않습니다. 대화가 10턴 이내로
짧고 실제 병목은 LLM 레이턴시이므로, 세션 상태를 서버에 저장하는 복잡도를 감수할
이유가 없습니다. eval 스크립트도 동일한 이유로 Python 변수로 상태를 직접
관리하며 외부 의존 없이 멀티턴을 시뮬레이션할 수 있습니다.

### 3.2 역할 분리 — 누가 무엇을 책임지는가

"무슨 기술을 연결했는가"보다 중요한 건 "누가 무엇을 책임지는가"입니다.

| 레이어 | 맡는 것 | 왜 여기인가 |
|---|---|---|
| **LLM** | 자연어 이해, 정책 분류, 상담 진행, 체크리스트 항목 추출·업데이트 | 시민 발화는 형식이 정해져 있지 않고, "위암인데 건강보험이에요" 같은 문장에서 무엇을 확인해야 하는지 매번 다르게 걸림 — 규칙으로 다 열거할 수 없는 유연한 판단이 필요 |
| **코드 / Rule** | 전화 판정 불가 항목 동결, 결정적 불가 조건 우선 적용, 확정값 보호, 출력 스키마 검증 | 틀리면 피해가 직접적이고 되돌릴 수 없는 지점 — LLM 프롬프트 지시만으로는 신뢰할 수 없는 제약이라 코드로 강제 |
| **사람 (상담원 / 담당자)** | 내방 안내 이후 실제 서류 확인, 최종 자격 판정, 세션 기록 참조 | 소득·재산처럼 시스템이 원천적으로 확인할 수 없는 판단, 그리고 예외 상황의 최종 책임 |

즉 **LLM의 능력을 강조하기보다, LLM의 한계를 시스템이 어떻게 통제하는지**가
이 설계의 핵심입니다. 구체적인 강제 방식은 §4에서 실패 시나리오 단위로 다룹니다.

## 4. 핵심 구현: 도메인 지식을 코드로 강제한 4가지 가드레일

판단은 LLM이 하지만, 아래 네 가지는 LLM 출력과 무관하게 코드가 강제합니다.
각각 "LLM에 맡기면 무슨 사고가 나는가"에 대한 대응입니다.

### 4.1 전화 판정 불가 항목 동결 (`confirmable_by == "visit"`)

소득·재산처럼 서류로만 확인 가능한 항목은, LLM이 무엇을 출력하든
**항상 `met: None`(미확인)으로 고정**합니다.

- 위험: LLM이 대화 맥락만으로 "소득 기준 충족"으로 단정 → 시민 오안내
- 대응: 체크리스트 항목마다 `confirmable_by: "phone" | "visit"` 플래그를 두고,
  `visit` 항목은 LLM 출력을 덮어써 미확인으로 강제

### 4.2 결정적 불가 조건을 LLM 판단보다 우선 (`INELIGIBLE_SIGNALS`)

건강보험 가입자의 2021.7.1 신규지원 중단 같은 cutoff 조건에서,
LLM이 근거(reasoning)로는 "신규지원 중단"을 인정하면서도 결론은
"지원 가능"으로 내는 불일치가 자주 발생합니다.

**원칙**: 정책상 결정적인 불가 조건이 검출되면, LLM의 최종 판단보다 그 조건을 우선한다.

```
LLM 출력 (applicable + reasoning)
   │
   ▼
정책상 불가 신호 검출
   ├─ 있음 → applicable = false 로 교정
   └─ 없음 → LLM 결과 유지
```

**현재 구현의 한계**: 이 검출은 reasoning 텍스트의 키워드 매칭입니다
(`src/rag/generator.py:213`). 정책 조건을 구조화된 규칙 데이터로 분리하지 않은
잠정 구현이며, 규칙 데이터로 승격하는 것을 다음 단계로 두고 있습니다.

### 4.3 확정값 보호

이미 `true`/`false`로 확정된 체크리스트 항목을, LLM이 이후 턴에서
`null`로 되돌리지 못하도록 코드로 차단합니다. 상담이 진행될수록
상태가 흔들리지 않게 하는 장치입니다.

단, 확정값 사이의 정정(`true → false`)은 허용합니다. 상담 중에 시민이 앞서 말한 내용을
바로잡는 일은 정상이기 때문입니다. 차단하는 것은 **확정된 사실이 미확인 상태로 되돌아가는 것**뿐입니다.

### 4.4 LLM 출력 구조 검증

function calling은 스키마를 **유도**할 뿐 보장하지 않습니다. 실제 eval 실행 중
두 가지 위반이 관측됐고, 둘 다 500 에러로 이어졌습니다.

- `arguments`가 깨진 JSON — 반복 생성으로 56KB까지 늘어난 뒤 파싱 실패
- 배열 원소가 객체가 아닌 문자열 — `recommendations`, `checklist_updates` 양쪽에서 발생

대응은 재시도 1회 + 구조 검증입니다. 스키마를 지키지 않은 항목은 조용히 버립니다.
**잘못 해석해서 상태를 오염시키는 것보다 업데이트를 누락하는 쪽이 안전하기 때문입니다**
(누락은 다음 턴에 다시 물어보면 복구되지만, 오염된 상태는 상담 끝까지 남습니다).

다만 상담 문구(`message`)가 비어 오는 경우에는 대체 문구를 만들지 않고 에러를 냅니다.
없는 답변을 코드가 지어내면 그게 곧 오안내이기 때문입니다.

> 위 4가지 중 **1·3·4는 `tests/test_guardrails.py`에서 LLM 없이 결정적으로 검증**합니다.
> 2번(정책 불가 조건 우선)은 LLM이 생성한 텍스트에 의존하므로 결정적 검증 대상이 아닙니다.

## 5. RAG는 왜 이렇게밖에 안 썼는가

일반적인 RAG 프로젝트라면 이 지점이 가장 공들이는 부분이겠지만, 이 시스템에서는
의도적으로 그렇게 하지 않았습니다.

> 정책 문서가 3개뿐이어서 검색의 선별 자체가 핵심 문제가 아니었습니다.
> 따라서 전체 정책 문서를 컨텍스트로 제공하고, 핵심 문제를 체크리스트
> 상태 관리로 옮겼습니다.

즉 **"RAG를 썼다"가 아니라 "RAG가 핵심이 아니라고 판단했다"**는 것이 이
설계에서 중요한 부분입니다. 청킹도 하지 않습니다(`src/rag/retriever.py:14`,
`n_results = collection.count()`로 항상 전체 문서 반환) — 조건이 여러 조항에
분산된 정책 문서 구조에서, 청킹이 오히려 조건들을 서로 다른 청크로 갈라놓아
맥락을 끊을 위험이 있었기 때문입니다.

## 6. 도메인 지식

### 6.1 출처

공공기관 공개 자료를 크롤링해 수집하고 GPT-4o로 구조화한 뒤,
현장 업무 지식이 필요한 부분은 수작업으로 보정했습니다.

| 데이터 | 출처 | 형태 |
|---|---|---|
| 정책 문서 3종 | 하남시 보건소, 질병관리청 헬프라인 | 크롤링 후 GPT-4o로 구조화한 마크다운 |
| 희귀질환 코드 1,413건 | 질병관리청 헬프라인 142페이지 | CSV (병명 / KCD코드 / 산정특례코드) |
| 보건소 부서 연락처 | 하남시 보건소 조직도 | JSON |

희귀질환 조회는 사용자 발화에서 병명·KCD 코드를 CSV와 문자열 매칭해
"공식 대상 질환" 근거를 LLM 컨텍스트에 제공합니다.
다만 **질환 매칭 결과만으로 자격을 확정하지 않습니다.** 보험 유형은 체크리스트 항목으로
남고, 소득 기준은 `visit` 항목이라 전화 상담에서는 미확인으로 동결됩니다.

크롤링 대상 페이지(하남시 보건소, 질병관리청 희귀질환 헬프라인)가 정적
렌더링임을 직접 확인한 뒤 Playwright 대신 BeautifulSoup으로 수집했습니다 —
브라우저를 띄울 이유가 없는데 띄우는 것은 불필요한 복잡도였습니다.

### 6.2 현업에서 발견한 암묵지 반영 이력

필자는 하남시 보건소 만성질환팀 상담원으로 근무한 경험이 있습니다. 이 시스템은 그 경험에서
얻은 실제 상담 업무 지식(암묵지)을 코드·데이터·프롬프트에 직접 반영하는 방식으로 품질을
높여갑니다. 크롤링이나 공개 문서만으로는 알 수 없는, 실제 상담 과정에서만 드러나는 지식이
어디에 어떻게 녹아 있는지 기록합니다.

#### ① 건강보험 가입자 암의료비지원 신규지원 중단 (2021.7.1)

**지식**: 보건소 암의료비지원의 건강보험 가입자 성인 암환자 대상은 2021년 7월 1일부터 신규 지원이 중단됐다. 2021.6.30까지 국가암검진 수검 후 수검일 기준 만 2년 이내 진단받은 자만 해당된다. 건강보험료 기준도 별도로 있다.

**왜 중요한가**: 크롤링 시 LLM이 이 조건을 요약 과정에서 누락했다. 정책 문서에 이 조건이 없으면 시스템이 건강보험 가입자에게 지원 가능하다고 잘못 안내한다.

**반영 위치**:
- `src/data/policies/암의료비지원.md` — 선정 기준에 신규지원중단 조건 및 건강보험료 기준 명시
- `src/rag/generator.py` — reasoning에 "지원 불가능" 키워드가 있으면 `applicable: false`로 강제 교정

#### ② 건강보험 가입자 대안: 건강보험공단 재난적 의료비 지원

**지식**: 보건소 암의료비지원이 불가한 건강보험 가입자에게는 국민건강보험공단(1577-1000)의 재난적 의료비 지원 사업을 안내하는 것이 실제 상담 프로세스다.

**반영 위치**:
- `src/data/policies/암의료비지원.md` — 신규지원중단 조건 설명 말미에 "건강보험공단(1577-1000) 재난적 의료비 지원 사업 요건 확인 안내" 명시

#### ③ 국가암검진 문의의 성격

**지식**: 국가암검진 관련 전화는 암 확진 환자가 치료비 지원을 요청하는 것이 아니다. 검진 통보서(안내 우편)를 받은 시민이 어느 병원에서 검진을 받으면 되는지를 묻는 것이다.

**왜 중요한가**: AI 시민 페르소나를 "암 진단 후 지원 문의"로 설정하면 실제 상담과 완전히 다른 시나리오가 만들어진다. 시스템 검증이 무의미해진다.

**반영 위치**:
- `frontend/src/app/page.tsx` — 국가암검진 관련 프리셋 시나리오를 "검진 통보서를 받고 어디서 검진받으면 되는지 문의"로 수정

#### ④ 건강보험 가입자 암의료비지원 — 이분법이 아닌 삼분법

**지식**: "건강보험 가입자 = 지원 불가"는 틀린 이분법이다. 2021.6.30 이전 국가암검진 수검 + 2023.6.30 이전 암 진단 + 건강보험료 기준 충족 시 지원 가능한 케이스가 실제로 존재한다. 최초 구현은 건보가입자를 확인하는 즉시 상담을 종료했다.

**왜 중요한가**: 조건을 충족하는 시민에게 "안 됩니다"라고 잘못 안내하는 False Negative 케이스다. 지원을 놓치는 쪽의 피해는 헛걸음보다 더 크다.

**AX 설계 원칙**: 체크리스트 항목은 상담 프로세스의 분기 흐름을 그대로 반영해야 한다. 보험 유형 확인 후 의료급여라면 이후 건보 전용 항목을 스킵하고, 건보라면 수검일·진단일을 추가 확인하는 분기가 체크리스트 라벨 설계에 명시돼야 한다.

**반영 위치**:
- `src/rag/generator.py` — 수검일·진단일·보험료 항목 추가, "(건강보험 가입자만)" 라벨로 분기 명시
- `src/rag/counselor.py` — 건보가입자 즉시 종료 → 수검일/진단일 확인 후 조건부 분기
- `src/data/policies/암의료비지원.md` — "신규지원 중단" 표현 → "조건 충족 시 가능"으로 수정

#### ⑤ 정책 문서가 스스로와 모순되면 LLM은 더 단정적인 문장을 따른다

**지식**: 삼분법 조건(2021.6.30 이전 수검 + 2023.6.30 이전 진단 + 보험료 기준)은 지금도
유효하다. 다만 조건 특성상 새로 충족하는 것이 사실상 불가능해서 **해당자가 극히 드물 뿐,
"건강보험 가입자는 신청 불가"가 아니다.**

**어떻게 발견했나**: eval S03(2020년 수검 + 2022년 진단 = 조건 충족)가 계속 실패해서
reasoning을 열어보니 *"2021.7.1부터 신규지원 중단으로 지원 자격이 없습니다"* 였다.
정책 문서를 확인하니 같은 문서 안에 상반된 두 문장이 있었다.

```
58행: 아래 조건을 모두 충족한 경우에만 지원 가능 (희박하나 실제 케이스 존재)
67행: ※ 현 시점(2026년) 신규 신청 불가 — 기한이 2023.6.30으로 이미 종료됨
```

LLM은 둘 중 더 단정적인 67행을 따랐다. §4-2의 프롬프트와 코드는 삼분법으로 고쳤지만,
**정책 문서에 남아 있던 옛 이분법 문장이 조용히 결론을 뒤집고 있었다.**

**왜 중요한가**: 조건을 충족하는 시민을 거절하는 False Negative이고, 원인이 코드가 아니라
데이터에 있어서 프롬프트만 고쳐서는 재현이 멈추지 않았다. 같은 지식을 코드·프롬프트·문서
세 곳에 반영할 때 **한 곳만 갱신하면 나머지가 이긴다.**

**반영 위치**:
- `src/data/policies/암의료비지원.md:67` — "신규 신청 불가" → "해당자는 매우 드물지만
  조건 충족 시 신청 가능. 건강보험 가입자라는 이유만으로 불가 안내하지 말고 수검일·진단일을 확인할 것"

**남은 문제**: 이 수정으로 S03가 통과하는 실행이 생겼지만, 대신 판단이 **불안정**해졌다.
결정적이지만 틀린 규칙("무조건 불가")을 걷어낸 자리에 LLM의 판단이 들어왔기 때문이다.
§7의 S02·S03가 실행마다 뒤집히는 것이 그 결과이고, 이 조건은 문서가 아니라 코드 규칙으로
옮겨야 한다는 것이 측정으로 확인된 셈입니다.

## 8. 실제 동작

데모 영상이나 스크린샷은 아직 찍어두지 않았습니다. 대신 §7의 C03 시나리오가
실제로 어떻게 흘러가는지, 로그에 남은 흐름 그대로 옮깁니다 — 이 시스템이
"삼분법 분기 + visit 동결"을 실제로 어떻게 처리하는지 보여주는 사례입니다.

**시민 설정**: 건강보험 가입자, 2020년 5월 국가암검진 수검(2021.6.30 이전),
2022년 3월 위암 진단(2023.6.30 이전).

```
시민: 건강보험 가입자인데 위암 진단을 받았어요. 보건소에서 지원을 받을 수 있나요?

  → classify(): "성인암의료비지원" 정책 선별, 체크리스트 초기화
    [보험 유형 확인, 진단 암종 확인, 국가암검진 수검일 확인,
     암 진단일 확인, 건강보험료 기준 충족(visit)]  전부 met: None

AI: 위암 진단을 받으셨군요. 보험 유형이 건강보험이라고 하셨는데,
    혹시 국가암검진을 언제 받으셨는지 알 수 있을까요?

  → 체크리스트 업데이트: 보험 유형=true, 암종(위암)=true

시민: 2020년 5월에 받았어요.

  → 체크리스트 업데이트: 수검일 조건(2021.6.30 이전)=true

AI: 그러면 암 진단은 언제 받으셨나요?

시민: 2022년 3월이요.

  → 체크리스트 업데이트: 진단일 조건(2023.6.30 이전)=true

AI: 수검일과 진단일 조건은 충족하십니다. 다만 건강보험료 기준(직장가입자
    127,500원 이하 / 지역가입자 60,000원 이하)은 전화로 확인이 어려워
    보건소 방문 시 서류로 확인해 드려야 합니다. 방문하실 때 건강보험료
    납부확인서를 지참해 주시면 안내해 드리겠습니다.

  → 코드 가드레일: 건강보험료 항목은 confirmable_by: "visit" →
    LLM이 무엇을 말하든 met: None 으로 강제 고정
  → expected_termination: "방문안내" 로 수렴
```

여기서 실제로 확인되는 것은 두 가지입니다.

1. **"건강보험 가입자 = 지원 불가"라는 틀린 이분법으로 즉시 종료하지 않고**,
   수검일·진단일을 순서대로 물어 삼분법 분기를 실제로 밟습니다(§6-2 ④).
2. **보험료 조건은 대화가 아무리 자연스럽게 흘러도 "충족"으로 확정되지 않습니다.**
   LLM이 이 턴에서 뭐라고 답했든, 코드가 마지막에 `None`으로 덮어씁니다(§4-1).

다만 이 흐름이 **3회 중 3회 모두 이렇게 깔끔하게 나온 것은 아닙니다** — §7.3에
적었듯 C05·C06처럼 체크리스트 업데이트가 누락되는 실행도 있었습니다. 위
로그는 성공한 실행 중 하나입니다.

## 10. 다음 문제: 보건소에서 발견한 더 일반적인 문제

§2에서 짚은 것처럼, 이 프로젝트에서 반복해서 문제를 일으킨 지점은 의료비
지원이라는 도메인 자체가 아니었습니다.

상담원이 고객의 상황을 파악하면서 동시에 관련 규정·조건을 찾아
**"지금 이 고객에게 무엇을 더 확인해야 하는가", "지금 이 결론을 내려도 되는가"를
계속 대조해야 하는 업무 구조**였습니다.

한 통화 안에서 상담원은 이 루프를 계속 반복합니다.

```
고객 발화
   ↓
현재 상황 파악
   ↓
관련 규정 확인
   ↓
필수 조건 확인
   ↓
예외 조건 확인
   ↓
현재 정보만으로 확정 가능한가?
   ↓
고객에게 안내
```

이 프로젝트에서 실제로 발생한 오류도 대부분 이 대조 과정에서 나왔습니다.
그리고 §3~4에서 만든 구조는 사실상 그 오류들에 하나씩 대응한 결과입니다.

| 대조 과정에서 발생한 문제 | 이 프로젝트에서의 대응 |
|---|---|
| 필요한 조건을 빠뜨림 (삼분법 사례, §6-2 ④) | 체크리스트 상태 머신 + 조건부 분기 |
| 규정과 결론이 불일치 (신규지원 중단 사례, §6-2 ①) | 결정적 불가 조건을 LLM 판단보다 우선 (§4-2) |
| 확인할 수 없는 정보를 임의 확정 | `confirmable_by: "visit"` 동결 (§4-1) |
| 확정된 상태가 이후 턴에서 흔들림 | 확정값 보호 (§4-3) |
| 문의 성격 자체를 오해 (국가암검진 사례, §6-2 ③) | 정책 분류 단계 분리 |
| 규정 문서가 스스로와 모순 (58행 vs 67행, §6-2 ⑤) | eval로 검출 → 문서 교정 |

즉, 문제의 본질은 **LLM이 정책을 모르는 것**이 아니었습니다.

> **상담원이 고객 상황과 업무 규정을 계속 대조하면서 발생하는
> 누락·불일치·근거 없는 확정을 어떻게 줄일 것인가.**

그리고 이 대조는 **매번 같은 결과가 나오지도 않습니다.** 같은 시나리오를 반복 실행하면
실패하는 지점이 매번 달랐습니다(§7 참고). 사람 상담원도 마찬가지입니다 — 오늘 빠뜨린
항목과 내일 빠뜨린 항목이 다릅니다. **그래서 "잘 아는 상담원을 만드는 것"으로는 부족하고,
매 건마다 대조가 제대로 됐는지 확인하는 층이 따로 필요합니다.**

이 프로젝트는 이 문제를 의료비 지원이라는 좁은 도메인 안에서 해결했습니다.
하지만 이 대조 루프는 특정 도메인에만 있는 게 아닙니다.
상담원이 내부 규정·FAQ·상품 조건·업무 절차를 참고하며 고객을 응대하는 업무라면
어디서든 같은 작업이 반복됩니다.

**보건소에서 자동화한 것은 상담 자체가 아니라, 상담원이 수행하던
반복적인 대조·검증 작업이었습니다.**

이 구조가 특히 복잡해지는 곳이 B2B 상담입니다. 고객사별 계약 조건, 요금제, 제품 정책,
예외 규정을 상담원이 동시에 확인해야 하기 때문입니다. 보건소에서는
`시민 상황 ↔ 지원 정책 ↔ 확인 가능 여부`를 대조했다면, B2B 상담에서는
`고객 상황 ↔ 계약·정책 ↔ 안내 가능 여부`를 대조합니다. **도메인은 달라도
상담원이 수행하는 검증 작업의 구조는 같습니다.**

**왜 하필 B2B인가**: 보건소에서 발견한 문제를 일반화하면, 규정과 조건을
기반으로 고객을 응대하는 업무에서 동일한 구조가 반복됩니다. B2B 상담은
고객 상황이 복잡하고, 계약·정책·요금·기능 조건이 존재하고, 예외 조건이
많으며, 상담원이 내부 규정과 고객 상황을 동시에 대조해야 하고, 잘못된
확정이 고객 신뢰나 계약에 영향을 줄 수 있다는 점에서 이 프로젝트의 구조를
도메인 밖에서 다시 검증하기에 적합한 다음 사례입니다.

### 그래서 다음 프로젝트로 이렇게 확장할 계획입니다

```
Project 01
보건소 의료비 지원 상담 AI
        │
        │ 구현 과정에서 반복되는 오류 관찰
        ▼
   Problem Discovery
"상담원의 문제는 지식 부족이 아니라
 규정과 고객 상황의 반복적인 대조다"
        │
        │ 의료 도메인 제거
        ▼
Project 02 (계획)
AI 상담원 업무 검증 Copilot

  상담 대화 + 업무 규정 + 고객 상태
                ↓
           AI Copilot
                ↓
   ┌──────────────────────┐
   │ 누락된 확인사항        │
   │ 규정 위반 가능성       │
   │ 근거 없는 확정         │
   │ 관련 근거              │
   │ 다음 행동              │
   └──────────────────────┘
```

다음 프로젝트에서는 문제를 "의료비 지원 상담 자동화"가 아니라
**"규정 기반 상담 업무의 실시간 검증"**으로 재정의하고, 의료 도메인을 제거해
B2B 상담 업무 전반으로 확장할 계획입니다. 아직 구현을 시작하지 않았고,
위 방향은 이 프로젝트에서 관측한 오류 패턴(위 표)을 근거로 세운 가설입니다.

> 상담원을 대체하는 AI가 아니라,
> **상담원이 규정에 맞게 업무를 수행하고 있는지 옆에서 검증하는 AI.**

## 11. 기술 스택

- **백엔드**: FastAPI, OpenAI SDK(GPT-4o, text-embedding-3-small), ChromaDB
- **프론트엔드**: Next.js 15 (채팅 패널 + 정책 체크리스트 카드 UI)
- **저장**: Supabase (세션·메시지·토큰 사용량 저장, 미설정 시 graceful skip)

**의도적으로 쓰지 않은 것들**:

- **LangChain** — 임베딩 → 검색 → LLM으로 이어지는 직선 파이프라인에 추상화
  레이어를 얹을 이유가 없었습니다. OpenAI SDK를 직접 호출하는 편이 어떤 문서가
  검색됐고 LLM에 무엇이 전달됐는지 디버깅하기 더 투명합니다.
- **정책별 전담 에이전트 (멀티 에이전트)** — 한 시민이 복수 정책에 동시에
  해당하는 경우가 많아서, 에이전트별 결과를 합산·조정하는 별도 조정자가
  결국 단일 LLM 호출과 같은 역할을 하게 됩니다. 조정자 하나를 더 만드는
  비용만 늘어나는 구조라 단일 RAG 파이프라인을 선택했습니다.
- **Playwright 크롤링** — 대상 공공기관 페이지가 정적 렌더링임을 먼저 확인하고
  BeautifulSoup으로 대체했습니다. 브라우저를 띄울 이유가 없는 곳에 띄우는 것은
  불필요한 복잡도입니다.

## 12. 실행 방법

### 요구사항

- Python 3.12, Node 18+
- OpenAI API 키 (필수). Supabase는 선택 — 비워두면 세션 저장을 건너뜁니다.

### 백엔드

```bash
python -m venv .health_venv
source .health_venv/bin/activate
pip install -r requirements.txt
```

`.env`에 아래 값을 채웁니다. `OPENAI_API_KEY`만 필수이고 나머지는 기본값이 있습니다.

```bash
OPENAI_API_KEY=          # 필수
CHROMA_PERSIST_DIR=      # 선택, 기본값 ./chroma_db
LLM_MODEL=               # 선택, 기본값 gpt-4o
SUPABASE_URL=            # 선택 — 비우면 세션 저장을 건너뜀
SUPABASE_ANON_KEY=       # 선택
```

```bash
python scripts/ingest_policies.py   # 정책 문서 3종을 ChromaDB에 인덱싱 (최초 1회)
uvicorn src.api:app --reload --port 8000
```

### 프론트엔드

```bash
cd frontend
npm install
echo "NEXT_PUBLIC_API_URL=http://localhost:8000" > .env.local
npm run dev
```

### 평가 재현

```bash
python tests/test_guardrails.py      # 코드 가드레일 15케이스 — 결정적, LLM·서버 불필요
python tests/run_eval.py             # /query 정책 분류 10 시나리오 — LLM 판단 포함, 서버 실행 필요
python tests/run_counselor_eval.py   # /chat 멀티턴 6 시나리오 — LLM 시민 시뮬레이터 포함
```

`run_eval.py`·`run_counselor_eval.py`는 LLM 호출이 개입해 §7에 기록한 것처럼
실행마다 결과가 다를 수 있습니다. 한 번의 실행 결과를 성능 지표로 읽지 않는 것을 권장합니다.

### 주요 엔드포인트

| 경로 | 역할 |
|---|---|
| `POST /classify` | 발화 → 해당 가능 정책 분류 |
| `POST /chat` | 멀티턴 상담. `messages`·`checklist`를 매 턴 클라이언트가 보유해 전달 |
| `POST /query` | 단일턴 정책 분류 (레거시 경로, eval에서 사용) |
| `POST /session-end` | 상담 세션 저장 (Supabase 미설정 시 생략) |
| `GET /health` | 헬스체크 |
