# 보건소 의료비 지원 상담 AI

RAG 기반 의료비 지원 정책 상담 시스템 — 보건소 복지 상담사를 위한 실시간 정책 안내 도구

---

## 문제 정의

보건소 복지 상담사는 전화 한 통으로 시민의 상황을 파악하면서 동시에 수십 가지 의료비 지원 정책 중 해당 여부를 즉각 판단해야 한다. 문제는 세 가지다.

1. **정책 복잡성** — 산정특례·의료급여·재난적의료비·희귀질환·장애인의료비 등 각 제도는 대상 질환, 소득 기준, 신청 절차가 모두 다르다.
2. **중복 해당 가능성** — "암 진단 + 저소득"처럼 한 시민이 여러 제도에 동시에 해당하는 경우가 많다. 하나만 안내하면 시민이 받을 수 있는 혜택을 놓친다.
3. **근거 제시의 필요** — 상담사가 시민에게 정책을 안내할 때 어떤 조항에 근거한 것인지 설명할 수 있어야 신뢰가 생긴다.

---

## 해결 과정의 사고

### "LLM만으로 안 되나?"

처음엔 GPT에게 "이 사람은 어떤 지원을 받을 수 있나요?"라고 물어보는 것을 생각했다. 문제는 **환각(hallucination)**이다. 복지 정책은 법령 조항 번호, 소득 기준 금액, 적용 질환 목록이 구체적으로 중요한데, LLM은 그럴듯하게 틀린 조항을 만들어낼 수 있다. 근거를 실제 문서에서 가져오는 구조가 필요했다.

### "RAG — 그런데 청킹이 필요한가?"

일반적인 RAG는 문서를 잘게 잘라(chunking) 일부만 검색한다. 그런데 이 시스템의 정책 문서는 단 5개이고, 각 문서는 하나의 제도 전체를 설명한다. 문서를 자르면 **"소득 기준은 1조에, 신청 방법은 3조에"처럼 맥락이 분산되어** LLM이 판단을 내리기 어려워진다. 따라서 청킹 없이 문서 전체를 벡터 1개로 저장하고, 검색 시 `top_k = 전체 문서 수`로 설정해 **항상 5개 문서를 모두 LLM에 전달**한다.

이 설계 덕분에 중복 해당 문제도 자연스럽게 해결된다. LLM이 모든 정책을 보고 각각의 해당 여부를 독립적으로 판단하므로, "산정특례도 되고 의료급여도 됩니다"라는 답변이 가능하다.

### "LangChain이 필요한가?"

초기 설계에는 LangChain이 있었다. 그런데 이 시스템의 파이프라인은 단순하다: `임베딩 → 검색 → LLM 호출`. LangChain은 복잡한 체인이나 에이전트 구성에 유용하지, 직선 파이프라인에 끼워넣으면 **추상화 비용만 늘어난다**. OpenAI SDK를 직접 호출하는 것으로 교체했다.

### "인용 검증을 코드로 해야 하나?"

검색된 문서와 LLM이 생성한 인용구를 fuzzy matching으로 대조하는 구조를 생각했다. 그런데 이건 **LLM이 실제 문서를 보면서 답하도록 유도하는 것**으로 해결할 수 있다. 시스템 프롬프트에서 "제공된 문서의 실제 조항 번호만 인용하라"고 명시하고, OpenAI function calling으로 응답 구조를 강제한다. 코드 복잡도를 낮추고 LLM의 능력을 신뢰하는 방향을 택했다.

## 시스템 구조

```
시민 전화
    │
    ▼
┌─────────────────────────────────────────────┐
│  Next.js 프론트엔드 (localhost:3000)          │
│  ┌──────────────┐   ┌─────────────────────┐  │
│  │ 피상담자 패널 │   │  AI 추천 패널        │  │
│  │ (채팅 입력)  │   │  (정책 카드 + 조항)  │  │
│  └──────────────┘   └─────────────────────┘  │
└────────────────────┬────────────────────────┘
                     │ POST /query
                     ▼
┌─────────────────────────────────────────────┐
│  FastAPI 백엔드 (localhost:8000)             │
│                                             │
│  쿼리 → 임베딩 → ChromaDB 검색             │
│       → 5개 정책 문서 전체 전달             │
│       → GPT-4o function calling             │
│       → 구조화된 JSON 응답                  │
└─────────────────────────────────────────────┘
```

**응답 구조 (정책별)**

```json
{
  "policy_name": "산정특례",
  "applicable": true,
  "eligibility_reasoning": "암 진단 시 산정특례 대상 질환에 해당합니다.",
  "source_excerpts": [
    { "text": "...", "article": "국민건강보험법 시행령 제19조" }
  ]
}
```

## 정책 문서

`src/data/policies/` 아래 5개 마크다운 파일. YAML frontmatter에 메타데이터를 정의하고, 본문 전체가 벡터로 저장된다.

- 산정특례 — 중증질환(암·희귀·중증난치) 본인부담 경감
- 의료급여 — 기초생활수급자·차상위계층 의료비 지원
- 재난적의료비지원 — 과도한 의료비 발생 시 한시적 지원
- 희귀질환의료비지원 — 희귀질환자 의료비 지원 사업
- 장애인의료비지원 — 장애인 의료급여 본인부담금 지원

## 실행 방법

### 1. 환경 설정

```bash
cp .env.example .env
# .env에 OPENAI_API_KEY 입력
pip install -r requirements.txt
```

### 2. 정책 문서 인덱싱

```bash
python scripts/ingest_policies.py
```

### 3. 백엔드 실행

```bash
uvicorn src.api:app --reload
# → http://localhost:8000
```

### 4. 프론트엔드 실행

```bash
cd frontend
npm install
npm run dev
# → http://localhost:3000
```

### 5. 평가 (선택)

```bash
# 백엔드 실행 상태에서
python tests/run_eval.py
# 5개 시나리오 recall=100% / precision=OK 확인
```
