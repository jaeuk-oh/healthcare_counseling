# 보건소 의료비 지원 상담 AI

RAG 기반 의료비 지원 정책 상담 시스템 — 보건소 복지 상담사를 위한 실시간 정책 안내 도구

---

## 문제 정의

보건소 복지 상담사는 전화 한 통으로 시민의 상황을 파악하면서 동시에 수십 가지 의료비 지원 정책 중 해당 여부를 즉각 판단해야 한다. 문제는 네 가지다.

1. **정책 복잡성** — 산정특례·의료급여·재난적의료비·희귀질환·장애인의료비 등 각 제도는 대상 질환, 소득 기준, 신청 절차가 모두 다르다.
2. **중복 해당 가능성** — "암 진단 + 저소득"처럼 한 시민이 여러 제도에 동시에 해당하는 경우가 많다. 하나만 안내하면 시민이 받을 수 있는 혜택을 놓친다.
3. **근거 제시의 필요** — 상담사가 시민에게 정책을 안내할 때 어떤 조항에 근거한 것인지 설명할 수 있어야 신뢰가 생긴다.

## 해결 과정의 사고

### "LLM만으로 안 되나?"

처음엔 GPT에게 "이 사람은 어떤 지원을 받을 수 있나요?"라고 물어보는 것을 생각했다. 문제는 **환각(hallucination)**이다. 복지 정책은 법령 조항 번호, 소득 기준 금액, 적용 질환 목록이 구체적으로 중요한데, LLM은 그럴듯하게 틀린 조항을 만들어낼 수 있다. 근거를 실제 문서에서 가져오는 구조가 필요했다.

### "RAG — 그런데 청킹이 필요한가?"

일반적인 RAG는 문서를 잘게 잘라(chunking) 일부만 검색한다. 그런데 이 시스템의 정책 문서는 단 5개이고, 각 문서는 하나의 제도 전체를 설명한다. 문서를 자르면 **"소득 기준은 1조에, 신청 방법은 3조에"처럼 맥락이 분산되어** LLM이 판단을 내리기 어려워진다. 따라서 청킹 없이 문서 전체를 벡터 1개로 저장하고, 검색 시 `top_k = 전체 문서 수`로 설정해 **항상 5개 문서를 모두 LLM에 전달**한다.

이 설계 덕분에 중복 해당 문제도 자연스럽게 해결된다. LLM이 모든 정책을 보고 각각의 해당 여부를 독립적으로 판단하므로, "산정특례도 되고 의료급여도 됩니다"라는 답변이 가능하다.

### "LangChain이 필요한가?"

초기 설계에는 LangChain이 있었다. 그런데 이 시스템의 파이프라인은 단순하다: `임베딩 → 검색 → LLM 호출`. LangChain은 복잡한 체인이나 에이전트 구성에 유용하지, 직선 파이프라인에 끼워넣으면 **추상화 비용만 늘어난다**. OpenAI SDK를 직접 호출하는 것으로 교체했다.

### "인용 검증을 코드로 해야 하나?"

검색된 문서와 LLM이 생성한 인용구를 fuzzy matching으로 대조하는 구조를 생각했다. 그런데 이건 **LLM이 실제 문서를 보면서 답하도록 유도하는 것**으로 해결할 수 있다. 시스템 프롬프트에서 "제공된 문서의 실제 조항 번호만 인용하라"고 명시하고, OpenAI function calling으로 응답 구조를 강제한다. 코드 복잡도를 낮추고 LLM의 능력을 신뢰하는 방향을 택했다.

### "상담사가 직접 입력하게 두면 안 되나?"

초기 설계는 상담사가 시민의 말을 받아 텍스트로 입력하는 구조였다. 그런데 실제 업무 흐름은 반대다. 상담사가 먼저 전화를 걸고, **시민이 상담을 요청하는 쪽**이다. 상담사 입장에서는 전화를 "받는" 경험이어야 했다. 그래서 시민 시나리오를 입력하면 AI가 시민 역할로 먼저 말을 걸고, 상담사가 답하는 멀티턴 구조로 바꿨다. 실제 전화 상담과 동일한 흐름이기 때문에 사용법을 따로 익힐 필요가 없다.

### "크롤링에 Playwright 대신 BeautifulSoup을 쓰는 이유"

Playwright는 실제 브라우저를 띄워 JavaScript를 실행한 뒤 결과를 가져오므로 동적 렌더링 사이트에 필요하다. 한국 공공기관 사이트는 상당수가 동적 렌더링이라 처음엔 Playwright를 고려했다. 그러나 크롤링 대상 페이지(하남시 보건소, 질병관리청 희귀질환 헬프라인)를 직접 확인한 결과 **페이지 소스에 본문이 그대로 포함된 정적 렌더링**이었다. 정적 사이트에 Playwright를 쓰면 브라우저 바이너리 설치 비용과 실행 오버헤드만 늘어난다. requests + BeautifulSoup으로 충분히 해결되므로 더 가벼운 선택을 했다.

### "정책별 전담 에이전트로 나눠야 하지 않나?"

희귀질환 에이전트, 암의료비 에이전트처럼 정책마다 전담 LLM을 두고 오케스트레이터가 라우팅하는 멀티 에이전트 구조를 검토했다. 결론은 **현재 단일 RAG 방식이 낫다**.

이유는 두 가지다. 첫째, 한 시민이 여러 정책에 **동시에 해당하는 케이스가 많다**("암 진단 + 의료급여 수급자" → 산정특례·암의료비지원 모두 해당). 에이전트를 분리하면 결과를 합치는 조정자가 반드시 필요하고, 그 조정자가 결국 지금의 단일 LLM과 같은 역할을 한다 — 복잡도만 늘어난다. 둘째, 정책 문서가 현재 3~5개 수준이라 전부 컨텍스트에 넣어도 토큰 부담이 없다. 이미 `classify()`로 관련 정책을 먼저 걸러내므로 사실상 암묵적 라우팅이 이뤄진다.

멀티 에이전트가 의미 있는 시점은 정책이 20개 이상으로 늘거나 에이전트마다 다른 외부 도구(공단 API, DB 조회 등)가 필요할 때다.

## 도메인 암묵지 반영 이력

이 시스템은 보건소 상담사의 실제 업무 지식(암묵지)을 코드·데이터·프롬프트에 직접 반영하는 방식으로 품질을 높여간다. 크롤링이나 공개 문서만으로는 얻을 수 없는 현장 지식이 어디에 어떻게 녹아 있는지 기록한다.

---

### 1. 건강보험 가입자 암의료비지원 신규지원 중단 (2021.7.1)

**지식**: 보건소 암의료비지원의 건강보험 가입자 성인 암환자 대상은 2021년 7월 1일부터 신규 지원이 중단됐다. 2021.6.30까지 국가암검진 수검 후 수검일 기준 만 2년 이내 진단받은 자만 해당된다. 건강보험료 기준도 별도로 있다.

**왜 중요한가**: 크롤링 시 LLM이 이 조건을 요약 과정에서 누락했다. 정책 문서에 이 조건이 없으면 시스템이 건강보험 가입자에게 지원 가능하다고 잘못 안내한다.

**반영 위치**:
- `src/data/policies/암의료비지원.md` — 선정 기준에 신규지원중단 조건 및 건강보험료 기준 명시
- `src/rag/generator.py` — reasoning에 "지원 불가능" 키워드가 있으면 `applicable: false`로 강제 교정

---

### 2. 건강보험 가입자 대안: 건강보험공단 재난적 의료비 지원

**지식**: 보건소 암의료비지원이 불가한 건강보험 가입자에게는 국민건강보험공단(1577-1000)의 재난적 의료비 지원 사업을 안내하는 것이 실제 상담 프로세스다.

**반영 위치**:
- `src/data/policies/암의료비지원.md` — 신규지원중단 조건 설명 말미에 "건강보험공단(1577-1000) 재난적 의료비 지원 사업 요건 확인 안내" 명시

---

### 3. 국가암검진 문의의 성격

**지식**: 국가암검진 관련 전화는 암 확진 환자가 치료비 지원을 요청하는 것이 아니다. 검진 통보서(안내 우편)를 받은 시민이 어느 병원에서 검진을 받으면 되는지를 묻는 것이다.

**왜 중요한가**: AI 시민 페르소나를 "암 진단 후 지원 문의"로 설정하면 실제 상담과 완전히 다른 시나리오가 만들어진다. 시스템 검증이 무의미해진다.

**반영 위치**:
- `frontend/src/app/page.tsx` — 국가암검진 관련 프리셋 시나리오를 "검진 통보서를 받고 어디서 검진받으면 되는지 문의"로 수정

## 시스템 개선 이력

### 1. 정책 판단을 매 턴 재생성하지 않고 체크리스트 방식으로 전환

**문제**: 채팅 메시지를 보낼 때마다 RAG → GPT function calling으로 전체 정책 판단을 재생성했다. 판단이 매 턴 바뀌어 불안정하고, 대화가 길어질수록 토큰 비용이 선형으로 증가했다.

**개선**: 2단계로 분리.
1. 시나리오 로드 시 1회: `/classify`로 관련 정책을 분류하고 체크리스트 항목을 모두 ⬜ 미확인으로 초기화.
2. 매 채팅 턴: `evaluate_criteria`로 대화에서 확인된 항목만 ✓/✗로 업데이트. 모든 항목이 ✓가 되면 지원 가능.

**효과**: 정책 판단이 안정적으로 유지되고, 매 턴 LLM 호출이 가벼워짐.

**반영 위치**:
- `src/rag/generator.py` — `POLICY_CRITERIA`, `classify()`, `evaluate_criteria()` 추가
- `src/api.py` — `/classify` 엔드포인트 추가, `/chat`에서 `rag_run()` 제거
- `frontend/src/components/PolicyCard.tsx` — 체크리스트 항목별 ✓/✗/⬜ 렌더링

---

### 2. 시민 페르소나 다양화

**문제**: 모든 시민이 동일한 프롬프트로 생성되어 말투가 균일했다. 실제 민원 전화는 말을 더듬는 사람, 단답형으로만 답하는 사람, 짜증섞인 말투 등 다양하다.

**개선**: 세션 시작 시 5가지 성격 유형(말더듬, 단답형, 짜증형, 민원형, 표준형) 중 하나를 랜덤 선택해 시나리오에 `[성격: ...]` 태그로 추가. `CITIZEN_SYSTEM` 프롬프트에 성격별 말투 예시를 추가해 LLM이 반영하도록 함.

**반영 위치**:
- `frontend/src/app/page.tsx` — `PERSONALITY_TYPES`, `withPersonality()` 추가
- `src/rag/citizen.py` — 성격 태그 해석 지침 및 말투 예시 추가

---

### 3. 상담 종료 버튼 + 세션 토큰 사용량 추적

**목적**: 체크리스트 방식 전환 전후 토큰 사용량 변화를 실측하기 위한 관측 도구.

**구현**: 상담 종료 버튼을 누르면 해당 세션의 토큰 사용량(입력/출력/합계)과 페르소나·턴수를 요약 모달로 표시하고, `logs/sessions.jsonl`에 append로 저장.

**반영 위치**:
- `src/api.py` — `/session-end` 엔드포인트 (JSONL append)
- `frontend/src/app/page.tsx` — `sessionTokens` 누적 state, 종료 모달 UI

## 시스템 구조

```
시민 전화
    │
    ▼
┌──────────────────────────────────────────────────┐
│  Next.js 프론트엔드 (localhost:3000)              │
│  ┌────────────────────┐  ┌─────────────────────┐  │
│  │   상담 채팅 패널    │  │   정책 체크리스트    │  │
│  │  (샘플질문 / 입력) │  │  (✓/✗/⬜ 실시간)   │  │
│  └────────────────────┘  └─────────────────────┘  │
└──────────────────┬───────────────────────────────┘
                   │ POST /chat
                   ▼
┌──────────────────────────────────────────────────┐
│  FastAPI 백엔드 (localhost:8000)                  │
│                                                  │
│  첫 턴: classify() — 관련 정책 분류 (Function Call)│
│                                                  │
│  매 턴: retrieve() — ChromaDB에서 전체 정책 문서  │
│         rare_lookup() — 희귀질환 CSV 키워드 매칭  │
│         counselor_response() — 상담사 답변 생성   │
│                               + 체크리스트 업데이트│
│                                                  │
│  코드 가드레일: INELIGIBLE_SIGNALS 패턴 교정      │
│               확정값(true/false) 보호             │
└──────────────────────────────────────────────────┘
                   │
                   ▼
            Supabase (세션/메시지 저장)
```

## 실행 방법

### 1. 환경 설정

```bash
cp .env.example .env
# .env에 OPENAI_API_KEY 입력
pip install -r requirements.txt
```

### 2. 정책 문서 인덱싱

```bash
python scripts/ingest_policies.py
```

### 3. 백엔드 실행

```bash
uvicorn src.api:app --reload
# → http://localhost:8000
```

### 4. 프론트엔드 실행

```bash
cd frontend
npm install
npm run dev
# → http://localhost:3000
```

### 5. 평가 (선택)

```bash
# 백엔드 실행 상태에서
python tests/run_eval.py
# 5개 시나리오 recall=100% / precision=OK 확인
```
